Using ComfyUI in Omni Studio

Start Comfy, prepare workflows, place model components across your GPUs, and verify results safely. Planning and dependency checks do not load model weights.

Recommended first run

  1. Open the ComfyUI tab. Select the GPU that should be primary.
  2. Enable component placement and check every auxiliary GPU you want Comfy to see.
  3. Start ComfyUI. Starting the engine does not load a model.
  4. Open Workflows and choose the running Comfy instance.
  5. Select Automatic pool, choose eligible GPUs, and leave reasonable VRAM reserve.
  6. Click Plan GPUs. Review component assignments, memory estimates, warnings, and blockers.
  7. Run only when the plan is valid. Confirm the final placement shown before queueing.
  8. Watch execution and verify output. “Queued” means accepted, not completed.

Placement modes

ModeUse it whenBehavior
Single GPUThe workflow fits on one card.Every discovered component targets the selected GPU.
Automatic poolRecommended default.The planner uses selected GPUs according to model size and current headroom.
Manual / hybridYou know a component should use a specific card.Your locked components stay fixed; everything else is planned automatically.

Warm reruns can reuse VRAM already owned by the selected Comfy process. Omni does this only when that process is the sole NVIDIA compute PID on the GPU; otherwise planning uses current free headroom so it does not crowd another application.

“Use all GPUs” means all selected cards are eligible. Omni does not force work onto a GPU when doing so provides no benefit. The advanced “require every GPU” option changes that and can block a plan.

This is component placement, not layer sharding. A diffusion model, text encoder, or VAE can use a different GPU. One individual model is not split layer-by-layer across cards.

Memory behavior

Omni’s staged MiniMax H3 workflow has strict phase boundaries: text encoder, diffusion model, video VAE, and audio VAE load and unload sequentially. Ordinary Comfy loaders can be routed to different GPUs but may remain resident together. The plan warns when a graph lacks strict staged unloading.

Keep VRAM reserve for Windows, the display, Comfy itself, and changing free-memory conditions. A valid estimate is a safety decision based on current information, not a promise that other applications will leave memory free.

Models and custom nodes

  • Workflow checks identify missing model files and node classes without loading models.
  • Comfy models live inside the distro under /opt/omni_studio/comfyui/models/<category>.
  • Verified Hugging Face downloads use Hub plus Xet and install into the selected Comfy category.
  • A queued download is not finished. Wait for the job and verify the file.
  • Deleting a model is immediate and not recoverable. Confirm its exact category and filename.
  • A custom-node repository is not considered working until its expected node classes load after restart.

Updates

Update Comfy core and Manager update-all are separate operations. A complete update performs them sequentially, restarts as required, and verifies both the core commit and loaded custom nodes. Do not run both updates concurrently.

A dry run is optional when you only want a preview. It is not required before an update you have explicitly approved.

When a plan is blocked

  • Restart required: the running Comfy instance was not started with a requested GPU in its pool.
  • Insufficient headroom: free VRAM minus reserve is below the estimated peak.
  • Missing model or node: install and verify the dependency, then check the workflow again.
  • API export needed: export the workflow in Comfy API format before queueing.

Do not bypass a blocker. Change the pool, workflow, model precision, workload size, or explicit placement and then generate a new plan.

For API users and agents

The detailed specification is stored with the app at docs/comfy-api.md. The app-owned agent skill is skills/omni-comfy-api/SKILL.md, and root AGENTS.md directs new agents to it automatically.

API schemas are typed in the gateway source. Interactive /docs and /openapi.json are intentionally disabled by default and are available only when a local development gateway starts with OMNI_ENABLE_DOCS=1.
